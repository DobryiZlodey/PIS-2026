### 2. Read Model

**Проекция:** `PortfolioViewOrm`

**Структура:**
- Денормализованная таблица: `portfolio_read_model`.
- Содержит поля верхнего уровня (например, `id`, `owner_id`, `status`, `total_positions_count`) для мгновенной фильтрации.
- Вложенные элементы (Positions, Transactions) сохраняются в виде JSONB строки (`view_data` поле в SQLAlchemy) без необходимости выполнять `JOIN` из таблиц Write модели при чтении. Это невероятно ускоряет отдачу данных клиентам.

**SQL-запрос EXPLAIN:**
Так как мы не делаем JOIN с позициями и транзакциями, план PostgreSQL для Query запросов выглядит как простой `Seq Scan` (по таблице `portfolio_read_model`), а если индекс настроен — `Index Scan`, что гарантирует получение полного графа данных портфеля мгновенно:
`Index Scan using ix_portfolio_read_model_portfolio_id on portfolio_read_model  (cost=0.15..8.17 rows=1)`

### 3. Event-Driven Sync

**События:**
- `PortfolioCreatedEvent` → вызов хендлера для создания новой записи в Read Model с пустым пулом позиций (JSON).
- `TransactionAddedEvent` → вызов хендлера для загрузки JSON из Read Model, добавления истории сделки и пересчета размера позиции In-memory, с последующим Update.
- `PortfolioClosedEvent` → обновление статуса в Read Model.

**Код:**
```python
    def handle_transaction_added(self, event) -> None:
        """
        Event payload assumed: {portfolio_id, tx_id, ticker, type, quantity, price, currency, timestamp}
        """
        db_view = self.db.query(PortfolioViewOrm).filter(PortfolioViewOrm.portfolio_id == event.portfolio_id).first()
        data = json.loads(db_view.view_data)
        
        # update transactions list
        data["transactions"].append({
            "id": event.tx_id,
            "ticker": event.ticker,
            "quantity": event.quantity
        })
        
        # simplified rolling update of positions view
        qty = event.quantity if event.type == "BUY" else -event.quantity
        pos_found = False
        for p in data["positions"]:
            if p["ticker"] == event.ticker:
                p["quantity"] += qty
                pos_found = True
                break
        
        if not pos_found and qty > 0:
            data["positions"].append({"ticker": event.ticker, "quantity": qty, "average_price": event.price})
            db_view.total_positions_count += 1
            
        db_view.view_data = json.dumps(data)
        self.db.commit()
```

## Контрольные вопросы

1. **В чём разница между CQRS и CQS?**
   CQS (Command-Query Separation) работает на уровне методов одного объекта (метод должен быть либо командой, либо запросом, но не обоими сразу). CQRS (Command-Query Responsibility Segregation) разделяет ответственность на архитектурном уровне: создаются раздельные модели, сервисы, базы данных для потока Чтения и Записи.

2. **Почему Read Model денормализованная?**
   Чтобы оптимизировать скорость чтения. Чтение происходит гораздо чаще записи, поэтому избавление от дорогостоящих операций JOIN позволяет базе данных отдавать информацию мгновенно за счет предварительной синхронизации-упаковки данных при записи.

3. **Как синхронизировать модели при сбое?**
   Можно использовать паттерн Outbox / Dead Letter Queue и механизм Retry, чтобы если проекция недоступна, событие сохранялось и переповторялось. А также можно полностью "перестроить" Read Model заново путем проигрывания (replay) всех событий из Event Store, если система базируется на Event Sourcing.

4. **Что такое Eventual Consistency?**
   Согласованность в конечном счете. Домен записывает изменения в агрегат, и операция считается успешной. Однако события для синхронизации Read Models идут асинхронно. Это означает, что клиент может прочитать старые данные из Read Model в первые миллисекунды после операции записи, но со временем (в конечном счете) Read Database синхронизируется и дойдет до консистентного состояния.
