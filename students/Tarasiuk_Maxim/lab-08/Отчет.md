## Ход выполнения работы

### 1. Portfolio Service (Request Service Analog)

**Bounded Context:** Управление портфелями и позициями инвестиционных активов. Сохранение истории транзакций пользователя и проверка лимитов, расчет средних цен покупки/объемов.

**API:**
- POST `/portfolios`
- GET `/portfolios/{id}`

---

### 2. Trading Service (Group Service Analog)

**Bounded Context:** Размещение ордеров на бирже, агрегация стоимости бумаг. Этот сервис взаимодействует с биржевыми поставщиками (API), отправляет запросы на покупку (BUY/SELL LIMIT), проверяет возможность такой сделки, и в случае успеха оповещает Portfolio Service через шину данных.

**API:**
- POST `/trading/orders`
- GET `/trading/orders/{id}`

---

### 3. Event Bus (RabbitMQ)

При возникновении события в одном сервисе (например, "Исполнен ордер на покупку акций Apple"), публикуется AMQP-сообщение в Message Broker. Остальные сервисы работают по шаблону "Publisher-Subscriber" и реагируют на события без жесткой связанности по HTTP.

**События:**
- `TradeExecutedEvent` (Публикуется в Trading Service -> Инициирует добавление Position в Portfolio Service).
- `PortfolioClosedEvent` (Публикуется в Portfolio Service -> Инициирует отправку уведомления в Notification Service).

**Скриншот RabbitMQ Management:**

_(Здесь должен быть скриншот интерфейса RabbitMQ Management (http://localhost:15672) со списками Exchanges и Queues у сервисов)_

---

### 4. API Gateway

**Маршрутизация:** Nginx используется в качестве Entrypoint-фасада для всех внешних клиентов.
- `http://localhost/portfolios/**` → проксируется на `portfolio_service:8000` (FastAPI).
- `http://localhost/trading/**` → проксируется на `trading_service:8001` (FastAPI).

**Конфигурация (nginx.conf):**
```nginx
events { worker_connections 1024; }
http {
    upstream portfolio_service { server portfolio_service:8000; }
    upstream trading_service { server trading_service:8001; }

    server {
        listen 80;
        location /portfolios { proxy_pass http://portfolio_service; }
        location /trading { proxy_pass http://trading_service; }
    }
}
```

---

### 5. Отказоустойчивость (Circuit Breaker)

В `trading_service` добавлен паттерн `CircuitBreaker`. При попытке синхронно обратиться к сторонним сервисам (например, API биржи для котировок) Circuit Breaker следит за таймаутами. Если ошибок > 3 (порог), Circuit Breaker переходит в состояние `OPEN` и сразу отбивает (`fast fail`) последующие внутренние запросы без долгих ожиданий. Через заданное время восстановления (`recovery_time`) он переходит в `HALF-OPEN`, чтобы проверить, жива ли сеть.

## Контрольные вопросы

1. **Что такое bounded context?**
   Bounded context (ограниченный контекст) - это граница внутри предметной области (Domain), внутри которой определенная доменная модель имеет строгий, непротиворечивый смысл и несет конкретные обязательства перед бизнес-процессом продукта. Это идеальные границы для выделения мироксервисов.
   
2. **Почему микросервисы не должны делить БД?**
   Деление (share) одной базы данных приводит к жесткой связанности (tight coupling) на уровне данных. Если один микросервис захочет изменить структуру своей таблицы, это сломает логику в другом сервисе (который её тоже читает). Изолированные БД позволяют развивать сервисы автономно, использовать разные СУБД (Polyglot Persistence) и избегать единой точки отказа (SPOF) блокировок транзакций.

3. **В чём проблема распределённых транзакций?**
   В монолите транзакция гарантирует свойства ACID. В микросервисах транзакция затрагивает несколько изолированных БД и сервисов по сети, что может привести к блокировкам на долгие промежутки времени при использовании Two-Phase Commit (2PC). Поэтому, вместо них прибегают к Сагам (Saga Pattern) и Eventual Consistency.

4. **Зачем нужен Circuit Breaker?**
   Это паттерн защиты от каскадных сбоев (Cascading Failures). Если сервис A (Gateway) вызывает сервис B (Trading), а сервис B завис и отвечает 30 секунд (TimeOut), то сервис A быстро исчерпает пулы потоков на ожидании ответа и тоже зависнет. Circuit Breaker обрубает цепь, если B начинает часто падать: запросы блокируются на клиенте моментально (Fast Fails), спасая A от зависания и давая B время на подъем.
