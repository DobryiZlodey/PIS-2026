### 1. Протофайлы (.proto)

Был описан контракт для **PortfolioService** с использованием IDL (Interface Definition Language) `proto3`.

**portfolio_service.proto:**
```protobuf
syntax = "proto3";

service PortfolioService {
  rpc CreatePortfolio(CreatePortfolioRequest) returns (CreatePortfolioResponse);
  rpc GetPortfolio(GetPortfolioRequest) returns (PortfolioDto);
  rpc StreamActivePortfolios(StreamRequest) returns (stream PortfolioDto);
}

message CreatePortfolioRequest {
  string portfolio_id = 1;
  string owner_id = 2;
}

message CreatePortfolioResponse {
  string portfolio_id = 1;
  string status = 2;
  string message = 3;
}

message GetPortfolioRequest {
  string portfolio_id = 1;
}

message StreamRequest {}

message PortfolioDto {
  string portfolio_id = 1;
  string owner_id = 2;
  string status = 3;
  int32 total_positions = 4;
}
```

### 2. gRPC Server

**Реализованные методы:**
В файле `grpc/server.py` реализован класс `PortfolioServicer`, переопределяющий (override) сгенерированные заглушки `grpcio`:
- `CreatePortfolio`: проверяет существование портфеля, возвращает `CreatePortfolioResponse` с кодом `ALREADY_EXISTS` при конфликте.
- `GetPortfolio`: осуществляет поиск, использует `context.set_code(grpc.StatusCode.NOT_FOUND)` при отсутствии портфеля.
- `StreamActivePortfolios` (server-side streaming): генератор `yield`, который стримит все открытые портфели, возвращая объекты `PortfolioDto` в реальном времени.

**Код:**
```python
    def StreamActivePortfolios(self, request, context):
        # Server-side streaming
        for port_id, port_dto in self.db.items():
            if port_dto.status == "ACTIVE":
                yield port_dto
                time.sleep(0.5) # Simulate real-time stream of updates
```

### 4. Server-Side Streaming

**Сценарий:**
Дэшборд администратора (клиент) подписывается на метод `StreamActivePortfolios(StreamRequest)` → сервер ищет все активные портфели и начинает отправлять их через `yield` по одному порциями (chunks), без разрыва HTTP/2 соединения, позволяя клиенту мгновенно их отображать в списке без ожидания загрузки всех 1.000.000 записей.

## Контрольные вопросы

1. **В чём преимущество gRPC над REST?**
   gRPC использует бинарный протокол Protobuf и HTTP/2 по умолчанию. Это делает его в 7-10 раз быстрее (компактнее payload), поддерживает мультиплексирование запросов и двунаправленный стриминг (bidirectional streaming), а также строго типизирован благодаря .proto-контрактам.
   
2. **Почему Protocol Buffers быстрее JSON?**
   JSON передает данные в виде длинного текста (строк), включая сами названия ключей (например, `{"first_name": "Ivan"}`). Protobuf передает бинарные пакеты, где поля кодируются числовыми индексами (тэгами). Благодаря этому, пакеты меньше весят и парсятся машинами мгновенно с использованием сгенерированных бинарных сериализаторов, минуя тяжелую конвертацию текста (string parsing).

3. **Зачем нужен streaming в gRPC?**
   Стриминг нужен для передачи большого объема данных без ожидания полной загрузки всех частей (снижение latency), а также для потокового вещания (real-time). В gRPC поддерживается Client-side streaming (клиент шлет поток, сервер ждет), Server-side streaming (клиент шлет 1 запрос, сервер отвечает потоком) и Bidirectional streaming.

4. **Когда использовать REST, а когда gRPC?**
   REST идеально подходит для публичных API (OpenAPI/Swagger), так как он "человекочитаем" в браузере (JSON), легко интегрируется с фронтендом и мобильными клиентами по простому HTTP/1.1. gRPC лучше использовать "под капотом" для внутреннего взаимодействия микросервисов (backend-to-backend), где критически важна низкая латентность и высокая пропускная способность.
